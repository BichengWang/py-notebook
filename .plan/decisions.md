# Decisions

Newest first. **Adopted** decisions are in force. **Proposed** decisions are
drafted from evidence and take effect when the owner marks them adopted (or
replaces them); until then the phase rows that depend on them stay blocked. Each
entry says what would reopen it. On 2026-10-19 the owner adopted the 2026-10-18
proposals (RFC 8785 after an explanation) and replaced the workbench proposal. The
GrowthBook-assertion and decision-control exact-replay entries record
implementation decisions already made in P-025 (#254) and in decision-control's
evaluation replay; they were added after the fact on 2026-10-19 and are not owner
proposals.

| 2026-10-22 | **Next record type, and only when an outside user brings such a decision: a score from a model the operator trains and hosts (P-033).** The non-goal "new decision points before an outside user asks for one" stands. A record for sampled actions from bandit or RL policies (P-035) comes second. Everything else fits an existing record or extends one, and also waits for an outside user (see [Model coverage](README.md#model-coverage)): binding LLM proposals to their raw output in decision-control (P-034), and image inputs, LLM-judge backends and per-query ranking metrics in `jevdecision` (no Plan ID until requested). Pilot outreach (P-027) opens by asking whether the team makes approve/decline decisions about people or accounts with a model it trains and hosts | Every current record re-checks a decision without re-running the model: Jev re-parses the stored provider response, and decision-control takes `Recommendation.probability` and `model` as the caller supplies them. With the operator's own model, a verifier can recompute the score from the features, a digest of the model file, the calibrator and the threshold, a stronger check than any record makes today. [Annex III](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:02024R1689-20260727) lists per-person scoring as high-risk: 4(a) recruitment and selection, 5(b) creditworthiness and credit scores (fraud detection excluded), 5(c) life and health insurance risk and pricing (read on EUR-Lex 2026-10-22). RELIA already trains such models (a logistic-regression baseline and a gradient-boosted candidate with an isotonic calibrator), but only inside its synthetic benchmark. It fits the adopted rules: the standard-library runtime (2026-10-12 entry) can score linear models, isotonic tables and tree ensembles exported as JSON; other model formats follow the OPA/Cedar pattern of P-015 (re-score when the runtime is installed, otherwise digest-only with a notice); `exp` in a logistic link falls under the 1e-9 tolerance rule | An outside user or pilot team brings a different kind of model first, or a pilot's decision needs P-033 before its protocol can freeze |
| 2026-10-22 | **Records follow the decision, not the model family: ranking and embedding models get no record type of their own.** A per-request ranking is an ordering, not a go/no-go decision. When the System One decisioner reranks, it asks one `Noul` per candidate ("is this document relevant to the query?") and sorts by probability; that is one Jev answer record with one question per candidate, which `jev-decision-verify` already replays. Use one `Noul` per candidate, not a single `Choice` over the candidates. Replacing a reranker, recommender or embedding model is a promotion decision: expgate for an online test, RELIA's `ranking_ndcg_gain` gate offline. A dedicated reranker stays a backend choice | A decisioner returns an absolute probability, which also sorts; a reranker's score only orders candidates within one query, so it cannot set a cutoff that means the same on every corpus. Third-party benchmarks, not reproduced here, put Jev with one `Noul` per candidate level with dedicated rerankers. [Kapa](https://www.kapa.ai/blog/jev-reranker-benchmark) (1,000 production queries, top 50): Jev 1.14 0.532, Voyage rerank-3 0.535, Cohere rerank-v4.0-pro 0.506. [hevmind](https://hevmind.com/writing/jev-as-a-reranker/) (three BEIR sets, BM25 top 30, nDCG@10): Jev 0.501, Voyage rerank-3 0.504, Cohere rerank-v3.5 0.486. Dedicated rerankers still win on slow outliers (a 30-document Jev call had a p95 near 1.4 s) and list length (a 32k-token Jev request holds about 50 passages). hevmind found a single `Choice` over the documents "much worse when many are" relevant, and a `Choice` holds at most 255 options | An outside user needs a per-request ranking audited as a decision, or uses Jev as a reranker and needs its ranking quality gated: `jev-decision-eval` scores each question pooled across cases (accuracy, Brier, log loss, ECE) and has no per-query NDCG or MRR, and RELIA's `ndcg_at_k` and `mrr` cannot be imported across components |

| 2026-10-19 | **The GrowthBook importer records operator-asserted snapshot facts and does not infer them** (P-025, #254). The results endpoint returns the latest snapshot together with the experiment's *current* settings, so the allocation share and the regression-adjustment state at snapshot time are not in the export. The mapping file's `snapshot` block asserts the expected treatment share and that the snapshot was not regression-adjusted; both are stored in `input.source.asserted`, covered by `input_sha256`, and the sample-ratio check uses the asserted share. The import is refused when the export's current weights or adjustment flags contradict an assertion. GrowthBook's own p-values, intervals and chance to win never feed the decision | An importer that guessed would present an unverifiable snapshot as a fact; recording the assertion in the digested input makes it visible, makes an edit detectable by the digest, and attributes it to the operator. Documented in the expgate README ("operator statements the importer cannot verify") | GrowthBook exposes snapshot-time settings in the export, or an export from a real user contradicts the assertion model |
| 2026-10-19 | **decision-control replay keeps exact comparison of recomputed metrics, with no tolerance**, because its evaluation arithmetic uses no platform-libm function: only IEEE 754 correctly rounded operations, `math.sqrt` and a fixed 95% quantile literal. A unit test fails if `evaluation.py` uses anything from `math` other than `sqrt`, imports a statistics or numeric library, calls `pow` or uses `**` other than `denominator ** 2`. Digests stay exact everywhere | The 1e-9 rule below exists because libm differs between platforms; where no libm function is involved, exact replay is portable and stricter, so a tolerance would only widen what a tampered report may pass ([decision-control README](../ai-workflows/decision-control/README.md)) | An evaluation metric needs `log`, `exp`, `erf`, float `pow` or an inverse CDF; the tolerance rule then applies to it |
| 2026-10-19 | **expgate verification and Jev re-scoring compare recomputed derived floating-point values at a relative tolerance of 1e-9, with a 1e-12 absolute floor where the expected value is exactly 0, for every schema version, old ones included.** decision-control replay stays exact (the entry above). Inputs, digests, strings, integers, booleans, dispositions and structure stay exact | 5 of 7 bundled expgate 0.1.0 records made on macOS failed exact replay on Linux, and the reverse failed too, because the platform libm differs in the last digits (guardrail z 1.9599639845400534 vs 1.9599639845400536). The change is backward compatible: nothing that verified before stops verifying | A record type needs bit-exact derived values |
| 2026-10-19 | **Adopt RFC 8785 (JCS) canonical JSON for the next schema version of every record type whose digest covers a re-serialized object**; current schemas keep their Python `json.dumps` form and readers (old readers kept). Integers are limited to the I-JSON safe range ±(2^53−1) | Python's `json.dumps` spells numbers `2.0` and `1e-07`, and a non-Python parser cannot recover int-versus-float, so other languages cannot recompute our digests. Measured on `experiment-gate/examples/offer-ranker-v2.json`: the Python digest is `c0b34a77…` and Node's is `c1ff2af0…`, from a single `2.0`. JCS is specified in informational RFC 8785 and has libraries in other languages; a short standard-library Python implementation (about 80 lines) lands with P-011/P-017. Cost: one new integer schema version per affected record type. Alternative not taken: specify Python's float repr as the canonical number form | A JCS port proves larger than the verifier it serves, or the I-JSON integer limit excludes a field a record needs |
